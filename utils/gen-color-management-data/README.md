# `gen-color-management-data`

Regenerates the fixtures and ICC profiles under `test_data/color_management/`.

> [!NOTE]
> **You usually don't need to run this.** The fixtures are committed, and
> re-running this script yields byte-identical files.

## What it produces

```text
test_data/color_management/
├── profiles/
│   ├── adobe-rgb-compatible.icc
│   ├── cmyk-ideal-inks.icc
│   ├── gray-gamma18.icc
│   └── srgb.icc
└── basic/
    ├── expected.tiff           (sRGB reference chart)
    ├── expected-gray.tiff      (sRGB reference gray ramp)
    └── <inputs>
```

Each data set has its own directory. In **basic**, every color is inside
8-bit sRGB and the common printable gamut, but stored and expressed in other
encodings. A **wide** data set, with colors outside 8-bit sRGB, is not
implemented yet.

Every page is one A4 chart of 4 × 6 uniform patches. Gray inputs show the
colors of `expected-gray.tiff`, all others those of `expected.tiff`.

### Images

| Input | Encoding |
| --- | --- |
| `rgb-untagged.tiff` | Untagged 8-bit RGB, meaning sRGB |
| `srgb.tiff` | 8-bit RGB with embedded sRGB profile |
| `rgb-16bit-untagged.png` | Untagged 16-bit RGB |
| `srgb-16bit.png` | 16-bit RGB with embedded sRGB profile |
| `adobe-rgb.{tiff,png,jpg}` | RGB with embedded Adobe RGB (1998)-compatible profile |
| `cmyk.{tiff,jpg}` | CMYK with embedded profile; the JPEG uses Adobe's inverted samples |
| `gray-gamma18.tiff` | Gray with embedded D50 / gamma 1.8 profile |

Images are 420 × 594 pixels at 50.8 DPI (51 in JPEG, whose density is an
integer). 16-bit samples are the exact 16-bit form of the 8-bit ones
(`v * 257`).

### PDF

Written directly by the script, so that each uses exactly one color space.

| Input | Content |
| --- | --- |
| `rgb-untagged-image.pdf`, `srgb-image.pdf` | 8-bit image in `DeviceRGB` / `ICCBased` sRGB |
| `rgb-16bit-untagged-image.pdf`, `srgb-16bit-image.pdf` | The same with 16 bits per component |
| `{adobe-rgb,cmyk,gray-gamma18}-image.pdf` | Image in `ICCBased` with the profile |
| `{adobe-rgb,cmyk}-jpeg.pdf` | `DCTDecode` image, profile in the PDF only; CMYK has `/Decode [1 0 …]` |
| `{rgb-untagged,adobe-rgb,cmyk,gray-gamma18}-vector.pdf` | Filled rectangles in `DeviceRGB` / `ICCBased` |

### XPS

| Input | Content |
| --- | --- |
| `<image>-{tiff,png,jpeg}.xps` | Each image above, byte for byte, as an `ImageBrush` |
| `srgb-vector.xps` | Paths filled with `#RRGGBB` |
| `scrgb-vector.xps` | Paths filled with linear `sc#` values |
| `{adobe-rgb,cmyk}-vector.xps` | Paths filled with `ContextColor` and the profile |

Vector patches use the 8-bit samples of the corresponding image.

## Checks

The references are specified directly as sRGB values. LittleCMS encodes the
other color spaces, except CMYK, whose samples the script computes from the
model of its profile. The script then reopens each image (including lossy
JPEG), converts it back with LittleCMS, and checks the center of every patch:

- All channels remain strictly between 8 and 247, away from sRGB clipping.
- Every channel is within 4/255 of the reference.
- Converting with the perceptual intent gives exactly the same colors as
  relative colorimetric, so the fixtures don't depend on the intent. With
  LittleCMS and a v4 sRGB, perceptual also implies black point compensation.

Each document is rendered with MuPDF, and every patch must be within 2/255 of
MuPDF's rendering of the image in the same color space. MuPDF ignores the
profiles of XPS `ContextColor`, so those documents are not rendered; their
samples are the same as those of the checked PDF paths.

Never derive references from rendered output, or relax these checks to accept
new fixtures.

## ICC profiles

The profiles embedded in the fixtures are also stored in `profiles/`.

- `srgb.icc` is generated by LittleCMS.
- `adobe-rgb-compatible.icc` is generated from the published D65 white,
  primaries (0.64, 0.33), (0.21, 0.71), (0.15, 0.06) and gamma 563/256. No
  Adobe-owned ICC binary is bundled.
- `gray-gamma18.icc` is generated from D50 and gamma 1.8.
- `cmyk-ideal-inks.icc` is a v2 CMYK input profile written by the script.
  Each ink absorbs its complementary sRGB primary in linear light, black
  absorbs all three, and sRGB's matrix gives the colors in XYZ. Its black is
  therefore absolute black, unlike that of real printing conditions, so black
  point compensation changes nothing. Its only table, `A2B0`, uses a 9-point
  grid that keeps LittleCMS within 2/255 of the model.

## Determinism

ICC creation dates are fixed, profile IDs cleared, and images have no
wall-clock metadata. PDF and XPS documents have no dates or IDs, and XPS ZIP
entries use a fixed timestamp. Upgrading Pillow/LittleCMS can change encoded
bytes; review the checks before updating fixtures. The current fixtures were
generated with Pillow 13.0.0 and LittleCMS 2.19.

## Dependencies

Python 3, Pillow with LittleCMS support, the LittleCMS 2 shared library and
`mutool` from MuPDF. On Arch Linux:

```bash
sudo pacman -S python python-pillow lcms2 mupdf-tools
```

## Usage

```bash
python utils/gen-color-management-data/run.py
```

Output goes straight into `test_data/color_management/`, overwriting any
existing files.
